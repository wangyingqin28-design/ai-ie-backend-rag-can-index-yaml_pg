# 动态资产提示词与知识提取联动设计

**设计时间：** 2026-07-06 11:33:10（Asia/Shanghai）

**实施范围：** `app/SQL_RAG/Asset_type_management`、`app/SQL_RAG/Knowledge_management`、`app/SQL_RAG/start-latest-full-stack.ps1`

**目标：** 通过真实资产管理界面维护公司、资产类型和三类提示词，由知识库界面动态选择并调用 SiliconFlow DeepSeek，完成解析、提取、精准入库和结果展示。

## 1. 已确认的业务约束

1. 测试产生的新资产、三类提示词和知识结果永久保留，使用秒级时间戳区分本轮数据。
2. 测试公司 ID 使用 `QY20001`，测试文件使用仓库根目录的 `新录音 4.m4a`。
3. 提示词类型保持数据库既有编码：
   - `1 = qa`：问答对提取，业务正文来自 `QA_EXTRACTION_PROMPT`。
   - `2 = intent`：意图识别，业务正文来自 `YT_PROMPT`。
   - `3 = decompose`：问题拆解和检索描述，业务正文来自 `DESCRIPTION_PROMPT`。
4. JSON 输出契约由提取链代码负责，不写入资产提示词表，避免 CRUD 操作破坏结构化入库格式。
5. 运行时只能使用数据库动态提示词，不允许以 Python 常量作为缺失配置的兜底。
6. 公司 ID、资产类型和三类提示词必须同时成立后才能执行知识上传。
7. 同一公司、资产和提示词类型存在多条启用记录时，按数据库顺序合并后共同作为该步骤的业务提示词。
8. 结果页展示标题按截图统一为：
   - `qa` → `知识标注提示词`
   - `intent` → `意图发现提示词`
   - `decompose` → `意图发现AI提取`

## 2. 当前执行链和保留边界

### 2.1 资产类型管理链

`Asset_type_management/webui/src/app.mjs` 负责资产和提示词编辑，`apiClient.mjs` 通过 WebUI 代理调用 FastAPI。`asset_type_service.py` 暴露资产与提示词 CRUD，`asset_type_repository.py` 将资产写入 `AI_ZiChanLeiXing`，将提示词写入 `AI_TiShiCiGuanLiBiao`。`asset_type_mapping.py` 维护 `qa/intent/decompose` 与 `1/2/3` 的双向映射。

### 2.2 知识库链

`Knowledge_management/webui` 先读取资产和公司选项，再读取所选组合的提示词包。上传请求携带 `asset_type_id`、`customer_id` 和 `gs_id`。`knowledge_api/app.py` 解析严格提示词包并调用 `process_uploaded_file`，后者串联文件解析、DeepSeek 问答提取、描述生成、意图提取及三张知识表入库。`response_mapper.py` 把原文、提示词块和知识卡片映射给结果页。

### 2.3 不改动的边界

- 不新增数据库表，不改变现有结果表字段。
- 不增加资产服务到知识服务的同步接口；两个服务以 PostgreSQL 为唯一共享事实来源。
- 不复制提示词到 Knowledge 前端本地状态作为运行时来源。
- 不清理或覆盖用户现有测试数据和未提交改动。

## 3. 严格动态提示词解析合同

输入必须包含非空 `asset_type_id` 和 `gs_id`。解析按以下顺序执行：

1. 从 `AI_ZiChanLeiXing` 查询 `zclxId = asset_type_id`、`gsId = gs_id`、未删除且在用的唯一资产记录。
2. 从资产记录取得 `tscId`，作为提示词工程关联主键。
3. 从 `AI_TiShiCiGuanLiBiao` 查询相同 `tscId`、相同 `gsId`、未删除且启用的提示词记录。
4. 将 `Tishicileixing` 严格映射到 `qa/intent/decompose`，未知编码直接报配置错误。
5. 每个类型按 `yima`、录入时间和提示词编码形成稳定顺序；同类多条以明确分隔符合并。
6. 三类均非空时生成 `promptOverrides` 和 `promptBlocks`；每块标记 `source=database` 并保留参与合并的提示词编码。
7. 缺少任一类型、资产与公司不匹配、提示词公司不匹配或存在无效类型时，返回可读的 4xx 配置错误，不调用 DeepSeek、不写结果表。

该合同替代 `prompt_repository.py` 当前的常量兜底逻辑。常量仅用于本轮通过资产管理 UI 建立测试数据以及独立的提示词模板维护，不参与知识上传时的运行时选择。

## 4. 前端联动设计

### 4.1 资产管理界面

1. 新建永久测试资产，名称包含 `20260706-HHmmss`，公司为 `QY20001`。
2. 保存资产后进入提示词工程界面。
3. 在三个 tab 中分别粘贴完整业务提示词并保存。
4. 列表应显示三类提示词及真实数据库返回的提示词编码、顺序和录入信息。

### 4.2 知识库界面

1. 资产下拉框与公司下拉框均由数据库选项接口加载。
2. 任一选择变化后重新请求严格提示词包。
3. 只有三块均为数据库来源时启用文件上传；否则在页面展示后端配置错误。
4. 上传 `新录音 4.m4a` 后展示解析中状态。
5. 完成后显示原始内容解析、三个指定标题的提示词块以及知识提取卡片。

## 5. 表字段与关联验收

### 5.1 核心四表

- `AI_ZiChanLeiXing`：新增一条资产；核验 `zclxId`、`gsId`、`ziChanLeiXing`、`tscId`、状态、调用规则和审计字段。
- `AI_TiShiCiGuanLiBiao`：新增三类提示词；核验相同 `tscId/gsId`、类型 `1/2/3`、启用状态、顺序、完整正文和审计字段。
- `AI_Wendajilu`：按本轮 `rawDataId` 查询问答；核验问题、答案、描述/标注、客户原文、客服原文、真实字段、`gsId` 和审计字段。
- `AI_Yitu`：按本轮 `rawDataId` 查询意图；核验意图、描述正文、证据、时间、`gsId` 和审计字段。

### 5.2 支撑表

- `AI_YuanShishuju`：按本轮 `rawDataId` 核验原始转写、资产 ID、客户关联、`gsId`、文件名和文件来源。

所有验证都使用本轮生成的主键定向查询，并记录执行前后行数；不能以表总行数代替关联验证。

## 6. 错误处理

- 资产或提示词保存失败：停留在资产管理界面，不进入知识上传。
- 严格提示词解析失败：Knowledge API 返回配置错误，前端禁用上传并显示错误详情。
- 文件解析或 DeepSeek 失败：返回真实 5xx/502 信息，不生成模拟知识卡片。
- 问答或意图结果为空：保留真实响应供诊断，但本轮端到端验收判失败。
- 任一目标字段关联错误、为空或使用了 fallback：本轮验收判失败。
